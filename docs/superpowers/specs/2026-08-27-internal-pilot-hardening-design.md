# 内部试用版安全与运维体验设计

## 目标

在不重写现有 WebUI、MCP 或 PAN-OS 调用链的前提下，把控制台提升为可供内部运维人员试用的版本：高风险变更可追溯、状态转换由服务端约束、首页能突出待处置问题，并为后续模块化与正式生产部署保留清晰边界。

## 已确认的边界

- 现有运行入口为 `webui/server.js`，WebUI 通过同一服务提供认证、任务、概览、飞书和 LLM 配置 API。
- MCP 层和直连 PAN-OS 路由已经存在；本轮不替换其通信方式，不引入微服务、消息队列或新数据库。
- 当前内部试用阶段**保持空闲会话超时关闭**。`IDLE_MINUTES` 继续为 `0`；不会因为本轮改造让用户在无操作后被自动退出。
- 保留单一内部管理员使用模型。本轮不引入多人 RBAC 或双人审批；但所有服务端状态转换必须为将来的角色与审批字段留出空间。
- 不读取、打印、提交或写入真实密码、API Key、设备 API Key、飞书凭据或会话令牌。
- 用户已有的 `cfgs/llm-choice.json` 与 `cfgs/tasks.json` 改动属于运行时数据，不能覆盖、格式化或提交。

## 目标架构

本轮采用“单进程、职责收口”的增量结构：

```text
WebUI
  -> HTTP API（认证、安全响应头、请求校验）
  -> 任务服务（状态机、计划指纹、审计事件）
  -> 工具路由（MCP / 直连 PAN-OS）
  -> 设备、LLM、飞书适配器
```

`webui/server.js` 仍是进程入口，但认证、安全响应头和任务审计会被提取为可独立测试的模块。页面只呈现状态和提交意图；任务状态转换、变更计划完整性与审计记录由服务端负责。

## 五个实施阶段

1. **基线与测试基础**：记录当前运行方式、保护用户运行时数据、为新模块引入 Node 内置测试。
2. **P0 安全与任务边界**：安全响应头、同源 API 认证约束、明确的服务端变更状态转换、任务审计事件与计划指纹。
3. **变更治理**：候选配置与 commit 前后记录计划版本、目标、防火墙、操作结果；前端展示可追溯的风险信息。
4. **总览与移动端**：把数据链路状态和设备健康告警分开，合并接口信息，确保窄屏上的关键操作可触达。
5. **回归与交付**：认证、任务状态、取消/拒绝、审计和首页关键状态的自动化测试及手工冒烟验证。

## 成功标准

- 所有新的安全/任务模块都有先失败后通过的测试。
- 不合法的任务状态转换不会调用 PAN-OS 工具，也不会改变任务状态。
- 每次创建、批准、拒绝、取消、候选执行和 commit 都生成结构化审计事件；清理界面任务不会清除审计事件。
- 认证 API、任务 API 和静态资源响应具备适合内部测试环境的基础安全头；空闲会话策略保持关闭。
- 首页明确展示数据采集状态与需要关注的设备事项，避免单一绿色状态覆盖许可证或接口异常。
- 现有 MCP 测试、WebUI 新增单元测试和本地页面冒烟测试通过。

## 非目标

- 不在本轮接入 SSO、完整 RBAC、双人审批或外部数据库。
- 不重写 WebUI 为新的框架，不修改 MCP 工具语义，不改变真实设备配置。
- 不启动真实变更任务作为测试；涉及 PAN-OS 的验证均使用状态机测试、模拟或只读检查。
