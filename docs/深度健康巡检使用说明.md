# 深度健康巡检：使用、架构与验收说明

更新日期：2026-09-21。本文对应 Route B 的三批原生接入，以及巡检中心的完整整合。

## 1. 本次交付范围

第一批基础 8 项、第二批扩展 21 项，以及第三批任务中心、中文报告、导出和回归验证均已实现。此次又迁入旧巡检的策略、WildFire、内容版本及日志链路观察，共 33 项检查，按 8 个运维分类展示。

这不等于当前防火墙的 33 项都能得到完整健康结论。设备型号、PAN-OS 版本、路由模式、功能配置及返回格式都会影响证据完整性；不支持、未配置证据不足、采集失败和真正告警是不同状态。

本次没有增加 Python 服务、第二套网站、数据库、任意 skill 执行器或定时任务。原“巡检中心”与深度巡检合并为“深度健康巡检”，不再保留两套新任务执行器；既有飞书桥接仅复用统一报告接口。

旧口令“完整巡检”“巡检”“inspect”仍可使用，但新建任务统一为 `monitor`。旧 `inspect` 任务的原始评级、结果和历史记录保留，不重算、不伪装成新版覆盖率。只删除当前 `webui` 运行链中已被替代的执行器和旧报告写入/推送读取路径，不删除历史报告文件或旧目录回滚副本。

## 2. 如何使用

刷新控制台，进入“任务中心”，点击“深度健康巡检”，或输入以下请求：

| 请求 | 范围 |
| --- | --- |
| `深度健康巡检` | 全部 33 项 |
| `完整巡检` / `巡检` / `inspect` | 同一种新版全量巡检，不再执行旧版 |
| `深度健康巡检 基础` | 基础 8 项 |
| `深度巡检 设备健康` | 指定分类 |
| `深度巡检 证书、许可证` | 指定检查项 |
| `深度巡检 威胁日志 最近5分钟` | 威胁日志，设备时间最近 5 分钟 |
| `检查证书` | 单项证书到期检查 |
| `深度健康巡检 策略最小权限、WildFire、内容库、日志链路` | 此次迁入的四项观察 |

分类名称：设备健康、资源性能、网络连通、安全策略、高可用、许可与订阅、远程接入与 VPN、SD-WAN。也可使用下表中的检查 ID。日志窗口默认 10 分钟，允许 1–60 分钟；其他指标保留自身的瞬时、采样历史或累计口径，不会被统一解释为“最近 10 分钟”。

执行时逐项展示进度。同一设备只允许一个深度巡检并发运行，可以使用任务原有“取消任务”动作终止。无需调用大模型来执行这些固定请求或判断告警。

如果自由表达仅被大模型归类为巡检，但检查范围未被固定解析器确认，系统会提示使用明确请求，不会擅自扩大为全量检查或丢弃用户要求的时间窗口。

完成后可以：

- 查看覆盖率、执行结果、风险等级和各类缺失数量。
- 按分类展开检查，风险优先排序；展开状态在任务轮询刷新后保留。
- 查看采集来源、时间、建议和脱敏证据预览。
- 导出结构化 JSON 或可离线打开的中文 HTML 报告。
- 明确确认后，推送该任务的报告摘要到当前配置的飞书会话；设置中的入口推送最新已结束巡检摘要。

菜单入口仍是填入请求，概览和任务快捷按钮仍按原有交互发起任务；只是统一名称与执行类型。飞书发起相同口令也走原有 `POST /api/task`，结束后的自动回执从同一份已保存报告取摘要。

## 4. 架构变化与原因

请求沿用现有链路：任务中心 → Task Planner → Task Service → Monitor Service → PAN-OS Adapter → MCP → 防火墙。

| 层 | 本次新增职责 | 为什么这样拆 |
| --- | --- | --- |
| Task Planner | 识别深度巡检、兼容旧口令、分类、单项和窗口 | 所有新入口走一个执行类型；不让自然语言直接拼接设备命令 |
| Task Service | 运行状态、同设备互斥、取消、审计、持久化、导出及通知摘要入口 | 状态和报告仍由唯一服务维护，避免两套存储和口径 |
| Monitor Service | 来源缓存、顺序采集、超时、覆盖率和报告组装 | 采集是否成功与设备是否健康分开判断 |
| 纯检查规则 | 8 个基础、21 个扩展及 4 个迁入检查 | 可通过真实形状 fixture 回归，不依赖大模型或网络执行测试 |
| Adapter | 固定只读来源、目标设备透传、安全错误和证书投影 | 复用现有认证，不新增凭据副本、不开放任意 XML |
| Router/UI | 受认证保护的目录及导出、中文报告和进度 | 复用登录、任务气泡与静态资源边界 |

关键目录是 `webui/services/monitor/`；浏览器报告渲染位于 `webui/assets/monitor-ui.js`。接口为 `GET /api/monitor/checks`、原有 `POST /api/task`、`GET /api/task/:id/monitor/export?format=json|html`。

报告唯一来源为 `task.result.monitor`：页面、导出和飞书摘要都读取它，不从旧 `reports/` 目录猜测最新报告。`GET /api/task/:id/monitor/notification` 是需认证的只读摘要接口；`POST /api/feishu/push-report` 可传 `{ "taskId": 123 }`，省略 ID 时选结束时间最新的已终态报告。运行中报告和旧版历史不作为新版通知来源；无指定报告返回 404，无最新报告返回 400，非法 ID 返回 400，GET 不触发发送。

飞书摘要保留任务 ID、设备、时间、执行状态、风险、覆盖缺口和优先风险，最多展示 10 条判断，发生截断明确提示；完整证据在同 ID 的 JSON/HTML 报告中。它是同一报告的摘要，而不是把完整文件全文塞进消息。既有飞书桥接对 monitor 任务最多等待 11 分钟（10 分钟采集预算加落盘余量），其他任务仍保持原 90 秒。

## 5. 数据与安全口径

- 只读：不创建候选配置，不 commit，不重启防火墙，不刷新 EDL，不执行自动修复。
- 目标设备经过原有 MCP 显式传递；没有跨设备回退到默认防火墙。
- 单个来源默认最多等待 30 秒，整次检查默认最多 10 分钟；相同来源在同次运行中复用。取消后的迟到数据不会完成任务。
- 原始异常不会直接进入报告；连接、认证、超时、命令兼容、时钟错误使用固定安全消息。
- 证书通过已有配置读取工具获取，只有名称、有效期等公开元数据进入报告；私钥和口令字段不保留。范围是 **candidate/shared**，不能当成已经部署生效的全部证书清单。
- 报告中的令牌、授权码、私钥、口令等字段脱敏。证据预览限量；结构化 findings 不受证据预览 50 条限制。扩展检查超过 100 个 findings 时保留优先风险并增加明确的覆盖缺口，不能静默丢弃后续告警。
- 报告下载需要现有登录认证，不在 URL 中携带令牌；HTML 对设备文字转义，不包含脚本或操作按钮。
- 本次没有修改已有的 **无操作 10 分钟重新认证** 策略。

特别纠正了上游规则中的几类误判：FIN 与 FAIL 分开判断；SD-WAN warning 不升级成 critical；BGP Active 不是 Established；缺失数据不能自动为零；累计计数不推导当前攻击或丢包速率；HA 只有明确关闭才是不适用；日志条数必须附带设备时间窗口和读取上限。

## 6. 资源、日志和兼容性边界

- MP CPU：`us + sy + ni` 的单次 OS 估算，明确标注；不是 load average，也不承诺与 WebUI 同期控制面均值一致。DP CPU：各核心、相应历史窗口内全部采样点的均值。缺少 DP 内存时保持未知，不能拿包缓冲替代。
- 接口：优先硬件状态视图，不把 ifnet 地址映射再算作一组接口。没有启用证据的 down 端口仅提示核对用途。
- 日志：设备时钟建立窗口，最多 1000 条；达到上限时仅表示已观察下限，不能宣称覆盖完整窗口。没有设备时间时不猜测时区。
- 安全规则命中目前只查询 vsys1；EDL 当前固定 IP 类型；GlobalProtect 来源仅为当前用户，不代表网关整体健康。
- 策略最小权限观察仅覆盖 **candidate/vsys1** 的显式启用 allow any-any 规则，不证明已提交运行配置或完整最小权限。规则缺少启用/动作/地址证据时保留未知；显式停用或拒绝规则不误报全放行。
- WildFire 仅验证已识别的连接/关闭状态，保留不同条目中的异常和缺失证据；连接正常不证明文件成功送检或安全策略已绑定。
- 内容库版本可展示，但没有发布时间和最新版本基准，不能证明已更新到最新；日志窗口内有记录也不能证明连续性、转发成功或没有丢日志。这两项相关判断明确为未知，因此全量报告可能合理显示“部分完成”。
- 流量和威胁日志均核对返回形状、计数和设备时间窗。日志链路检查与威胁日志检查复用同次运行采集；流量来源只保留窗口与计数，不额外存储整批流量明细。
- 日志配额中分配比例不等于实际占用率。只得到 Quotas 分配信息时，实际利用率保留未知。
- 区域防护使用设备自己的协议阈值；`dp0` 是处理器，不是丢包计数。累计丢包仅展示事实。
- 光模块空输出、未启用功能的空字符串、未识别文本不会变成“正常”。FQDN 的未知地址仍保留未知。
- 当前设备启用了 Advanced Routing，旧 routing/BGP/OSPF 路径被设备拒绝或标记废弃。该检查当前显示“不支持”，尚未扩展到 Advanced Routing 的逻辑路由器适配。应用统计、SSL 解密、SD-WAN、EDL 的当前固定查询也未在本设备取得支持证据；不是这几项已确认正常。

### 7.3 飞书命令启动故障修复（2026-09-21）

控制台发送消息时的 `spawn lark-cli ENOENT` 发生在本地子进程启动阶段：后台服务的 PATH 不包含已安装的飞书 CLI，所以尚未请求飞书就失败。这与没有可推送报告时返回的 HTTP 400 是不同问题。

本次增加 `webui/lib/feishu-runtime.js`，优先使用显式 `LARK_CLI`，其次查找 PATH 中的可执行文件，最后检测当前用户目录已有的 WorkBuddy CLI。该备用安装只在实际存在且可执行时使用，不引入安装依赖；找不到时保留可选功能原行为。发送消息和推送报告复用同一发送函数，子进程环境包含当前 Node 和 CLI 目录，不再修改全局 PATH，也未更换机器人身份、群配置或凭据。
